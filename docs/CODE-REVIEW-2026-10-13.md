## Находки

### HIGH / P1 — Смена даты может испортить посещаемость

Места: `web/src/pages/director/Classes.jsx:8`, `:51`;
`web/src/lib/useApi.js:11`.

При выборе даты B хук сохраняет данные даты A на время загрузки. Новый ключ
`key={`${c.id}-${date}`}` создаёт ClassRow для B со старым `present_count` из A.
`useState(cls.present_count ?? "")` не обновляется, когда приходит ответ B.
Даже после загрузки поле остаётся от A; кнопка OK записывает его в дату B.
Проверка максимума учеников не защищает от корректного числа для неверного дня.

Исправление: связывать данные и строку с датой ответа; скрывать/блокировать
редактирование при несовпадении дат. Инициализировать поля после загрузки
нужного дня. Проверить переключение между днями с разной посещаемостью.

### HIGH / P1 — Ссылки входа записываются в access log

Место: `server/src/app.js:43`: `app.use(morgan("tiny"))`.

Morgan tiny включает URL запроса. Открытие `/trayeye/l/<token>` записывает
секрет личной ссылки в stdout сервиса, который собирает systemd journal.
Этот токен позволяет входить без пароля до отзыва ссылки. Хэширование токена
в БД не защищает его копию в журнале. В production логирование включено.
Подтверждено запросом к локальному приложению с синтетическим токеном:
Morgan записал полный `/l/review-only-not-a-real-access-token`.

Исправление: редактировать URL перед логированием или исключить маршрут входа;
проверить аналогичную настройку access log прокси. Проверка: лог запроса
по синтетической личной ссылке не должен содержать её токен.

### MEDIUM / P2 — Нет данных камеры трактуется как измеренное списание

Места: `server/src/services/schoolData.js:20`,
`server/src/services/metrics.js:69`, `server/src/services/overview.js:33`.

SQL превращает отсутствие сканов в `trays=0, eaten=0`. Расчёт
`Math.max(0, r.planned - r.eaten)` считает все заказанные порции отходами.
В новой школе, утром до еды или при отключённой камере карточка показывает
100% списаний. При неполном покрытии камеры списания также завышаются.
Отдельно отсутствие сканов может попасть в исходный уровень и рекомендации.

Воспроизведено вызовом функции: заказ 100 порций по 50 ₽ без сканов даёт
5000 ₽ списаний и 100%; один полностью съеденный поднос даёт 99% списаний.

Исправление: явно учитывать полноту измерения/завершение дня; показывать
«нет данных» для неизвестного результата и исключать такие дни из baseline
и обучения прогноза. Текущая формула допустима только при полном учёте подносов.

### MEDIUM / P2 — Невалидный процент ИИ становится достоверным нулём

Место: `server/src/services/vision.js:72`: `Number(it?.leftover_pct)`.

`null`, пустая строка и `false` преобразуются в 0 и проходят Number.isFinite.
Ответ `{"items":[{"dish_id":1,"leftover_pct":null}]}` сохраняется как
полностью съеденное блюдо. Воспроизведено прямым вызовом parseItems.

Исправление: проверять исходный тип и диапазон до преобразования; отклонять
неизвестную оценку. Добавить проверки null, пустой строки и boolean.

### MEDIUM / P2 — Повторная загрузка одного подноса удваивает его учёт

Место: `server/src/routes/director.js:219`.

Каждый POST создаёт новый tray_scan. Повторное фото после сетевого сбоя
или повторного выбора файла снова увеличивает число подносов и съеденные
порции. Нет идентификатора события или проверки дубля; SQL считает все записи.
Это меняет списания, долю взявших блюдо и прогноз заказа.

Исправление: идентификатор события/идемпотентности с уникальным ограничением;
для ручной загрузки — согласованная проверка дубликатов в рамках школы и дня.
Повторная отправка одного события должна возвращать прежний результат.

### MEDIUM / P2 — Цена из каталога переписывает прошлую финансовую статистику

Места: `server/src/services/schoolData.js:18`,
`server/src/routes/kombinat.js` (PUT /dishes/:id), `server/src/db/schema.sql`.

Исторические строки меню используют текущую `dishes.portion_price` через JOIN.
После изменения цены блюда старые суммы заказа, списания и экономия
пересчитываются по новой цене. В меню нет снимка цены на дату заказа.

Исправление: хранить цену порции в позиции меню/заказа или использовать
версионированные цены. Проверить неизменность прошлого отчёта после смены цены.

### MEDIUM / P2 — «Дней в меню» комбината считает школы как отдельные дни

Место: `server/src/services/metrics.js:219`: `days: list.length`.

В сводной статистике одно блюдо в двух школах за два дня имеет четыре
строки dishDay. Интерфейс StatsView показывает «Дней в меню: 4» вместо 2.
Воспроизведено прямым вызовом dishStats с двумя школами и двумя датами.

Исправление: считать уникальные даты либо назвать метрику «школо-дни».

  в текущем приложении не подтверждён; обновление требует отдельной проверки.

  распознавания подносов этим ревью не проверялись.

  браузерное воспроизведение не проводилось. UI-тестов на этот сценарий нет.

  присутствуют; обходов этих проверок при чтении кода не обнаружено.
- Конфигурация работающего прокси и содержимое production-логов не проверялись.
- CI-шаблон находится в docs/ci-workflow.yml, а не в активном workflow тестов.
